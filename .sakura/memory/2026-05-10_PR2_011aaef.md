### 2. 发现的模式

- **模式：按需添加反爬头，而非统一设计**  
  开发者仅针对当前报错的方法添加了请求头，未考虑同类 API 调用的一致性。这是一种常见的“救火式”编码习惯，长期会导致技术债务。
- **架构观察：缺少请求基础设施抽象**  
  项目没有封装一个统一的 HTTP 请求方法（如 `_request()`），导致 headers、超时、重试等逻辑分散在各方法中。本次审查准确地指出了这一点。
- **依赖观察**：项目依赖外部 API (`touchgal.top`)，但未看到明确的错误降级或重试策略，脆弱性较高。

### 3. 规范完善建议

基于本次审查，可以为项目或团队新增以下审查规则：

| 规则ID | 规则名称 | 触发条件 | 建议严重度 |

| `http-client-reuse` | HTTP 请求配置未复用 | 同一类中对相似域名有 >=2 处网络请求，且 headers/超时配置未提取为公共方法 | minor |

### 4. 经验教训

- **关注变更的传递影响**：添加请求头解决了 A 接口，但 B/C 接口可能在未来某天突然失败。审查时应主动检查是否存在“相同目标域名的其他请求”。
- **反爬策略的脆弱性值得单独警示**：针对特定站点的反爬修复（如 UA、Referer）有明确的时效性。建议在评审意见中额外加一句：“建议监控该 API 后续是否再次失效，考虑更稳定的接入方式（如有官方 API）”。
- **不要仅审查新增代码行**：本次变更 +9/-1，审查者扩展检查了 `get_downloads`（未修改的行），这是高质量审查的表现。应作为最佳实践推广。
