## 近期审查模式总结

### 高频问题模式
1. **按需添加反爬头，缺乏统一设计**：仅针对报错接口添加请求头，同类API调用未同步更新，导致代码不一致和潜在故障。

2. **缺少HTTP请求基础设施抽象**：未封装统一的请求方法，headers、超时、重试逻辑分散在各方法中，增加维护成本和遗漏风险。

3. **硬编码敏感配置**：User-Agent包含具体版本号（如`120.0.0.0`），缺乏时效性管理，未来可能因版本过时被拒绝。

4. **403类错误的系统性遗漏**：修复单一接口时，未检查同一域名下其他接口是否也需要相同请求头。

### 架构观察
- 项目依赖外部API（`touchgal.top`），但缺少明确的错误降级和重试策略，脆弱性较高。
- 第三方API反爬策略变动频繁，需持续关注。

## 常见代码问题和审查要点

### 审查必检项
| 检查点 | 说明 |
|--------|------|
| 同域名所有请求 | 新增请求头时，扫描整个仓库中调用相同域名的所有方法 |
| 异常处理适配 | 请求头变更后，原异常分支（如超时）是否能正确处理新错误码（如403） |
| 请求配置复用 | 存在≥2处相似请求时，建议抽取为公共方法 |
| 浏览器模拟头 | 与Web API交互应默认添加UA、Referer、Origin等 |
| 403诊断清单 | 检查UA、Referer/Origin、x-requested-with、Cookie、IP状态 |

### 规范建议
| 规则ID | 规则名称 | 触发条件 | 严重度 |
|--------|----------|----------|--------|
| http-client-reuse | HTTP请求配置未复用 | 同类域名≥2处网络请求未提取公共方法 | minor |
| ua-version-stale | UA版本硬编码 | UA包含具体年份或大版本号（如120.0.0.0） | suggestion |
| api-fail-handle | API缺少统一失败处理 | 新增网络请求未使用已有错误处理包装器 | info |
| missing-anti-scrape-headers | 反爬头缺失 | 请求外部API时缺少Referer或x-requested-with | minor |

## 经验教训

1. **关注变更的传递影响**：修复A接口可能隐藏B/C接口的未来风险。审查时必须主动检查“相同目标域名的所有请求”。

2. **反爬策略有时效性**：针对特定站点的UA/Referer修复需单独警示，建议在评审意见中提醒监控后续是否再次失效。

3. **全量审查优于增量**：纯diff审查易遗漏跨方法的代码不一致。手动全量重审能发现代码重复和架构缺陷，但需明确列出所有审查过的文件路径。

4. **Issue处理最佳实践**：
   - 403错误优先检查UA、Referer、Origin、x-requested-with
   - 根因分析后必须反向验证可行性，给出具体修复方案
   - 标签不能为空，至少输出低置信度候选标签
   - 重复检测需附证据（引用原Issue的关键特征）

5. **可行性判断不能保守**：一旦定位到上游明确逻辑（如校验某请求头），就不能说“无法评估”，应给出具体方案和工作量。

## 需要特别关注的领域

### TouchGalAPI类改造
- 强制要求所有对外请求通过私有方法`_request(url, **kwargs)`发出
- 在该方法中统一添加headers、session管理、日志记录
- 所有请求头（UA、Referer、Origin、x-requested-with）集中配置

### 监控与告警
- 关注TouchGal API是否再次返回403，及时调整模拟策略
- 定期检查硬编码UA是否需要更新（建议移除具体版本号）

### 测试覆盖
- 修改请求头后，需验证`get_downloads`和`download_and_convert_image`等接口
- 建议添加对API返回403时的降级处理测试
- 验证添加请求头后是否引入新的异常处理需求
